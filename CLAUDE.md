# agent-webhook-bridge

A webhook receiver, classifier framework, and CLI for AI agents (or operators) integrating with the [kanban-board](https://github.com/your-org/kanban-board) app — and any other webhook-emitting upstream following the same shape. **A single Laravel app** (Laravel 13, PHP 8.5, MariaDB 10.6+ / SQLite for tests) on Apache + PHP-FPM. The receiver verifies the webhook, then classifies → stages to the inbox → runs handlers **synchronously in the same request**, returning 200 only when done — **no queue worker, no consumer cron, no daemon**. At-least-once delivery is borrowed from kanban-board's webhook retry (any internal failure → 5xx → re-delivered) — except a RATE-LIMITED durable writeback, which the bridge records as owed and retries itself (card#10849 / DL-440, `docs/writeback.md` § Failure behaviour) plus `inbox.jsonl` as the durable pull-backstop. See [`CLAUDE_ARCHITECTURE.md`](CLAUDE_ARCHITECTURE.md) + [`CLAUDE_DECISIONS.md`](CLAUDE_DECISIONS.md) DL-001. (v0.12 rewrote the v0.11.x PHP-receiver + Python-consumer split into this single runtime.)

> **If you're a future session of Claude (or any AI agent) opening this repo for the first time, this file is your map.** Read this index → jump to the relevant subfile per the "When to read" table below. The subfiles contain the load-bearing detail; this file should stay short.

## Standing rules

1. **Senior-dev review-agent loop before every PR.** Iterate review → fix → re-review until CLEAN. Do not skip. CI passing is necessary, not sufficient. See [`feedback-review-agent-loop-before-pr`](../.claude/projects/-home-kanban/memory/feedback-review-agent-loop-before-pr.md) memory note.
2. **Doc-sync in every PR.** Behavior changes update the affected subfile in the same PR. Decision-worthy changes append `DL-NNN` to `CLAUDE_DECISIONS.md`. Don't "document later." **The DL number is allocated, never derived from the log** (DL-295) — `CLAUDE_DECISIONS.md`'s own header owns the method and this line deliberately does not restate it.
3. **No secrets in the repo.** Per-`(provider, scope)` webhook secrets live at `<secret_dir>/<provider>/webhook-secret-scope-<scope>` (chmod 600); the DB password lives in the Laravel `.env` (`DB_PASSWORD`); API tokens live by convention at `<secret_dir>/<provider>/token` (per-agent `api.<provider>.token_path` is an optional override). `secret_dir` defaults to `BRIDGE_DIR`. `.env`, the secret dir, and `~/.config/...` are outside the repo / gitignored. `.env.example` and `examples/sample-config/agent.yml.example` are the templates that DO ship.
4. **Two-branch workflow: `main` + `dev`.** `dev` is the integration branch where all feature work lands. `main` is the release branch — only the user merges to it (typically via a release PR from `dev`). All feature branches PR back to `dev`. Matches the kanban-board project's workflow.
5. **Open dev-targeted PRs autonomously; self-merge on green CI; never merge to `main`.** Per [`feedback-git-workflow`](../.claude/projects/-home-kanban/memory/feedback-git-workflow.md) (canonical for both agent-webhook-bridge AND kanban-board): the whole dev-PR lifecycle — open → wait-for-green → self-merge — is **pre-authorized**. **No ask** to `gh pr create` a dev-targeted PR (the open-checkpoint ask is retired), and no second ask to merge it — merging validated work into `dev` is just integration. **Wait for EVERY CI workflow that ran on the head SHA to complete + pass before self-merging — read the list from the Actions API, do not recall it.** Deliberately NOT an enumeration any more: the previous wording listed four workflows by name, `bin/ python unit tests` was added later and never joined the list, and a reader following the rule literally would have self-merged over a red one (card#5575). A named list of checks is a second copy of `.github/workflows/`, and it drifts the moment a workflow is added. **Hard gate: only the user merges PRs to `main`** — even on green CI; AI sessions may open `main`-targeted (release) PRs but must never run `gh pr merge` against one. The post-release back-merge sync PR and the automatic tag are owned by [`VERSIONING.md`](VERSIONING.md) steps 10–12.
6. **Bridge code stays out of the kanban-board repo.** Customer-side infrastructure lives in its own git repo for lifecycle decoupling. Same rationale as `kbcard` living in `~/.local/bin/` not `kanbanboard/bin/`.
7. **Per-agent installations, not shared.** Two agents (e.g. `prod-agent` + `dev-agent` on the canonical reference install, or any operator-chosen pair of identities) running on the same host install their own bridge copies with their own DBs. No shared runtime state across agents. See [`CLAUDE_DEPLOYMENT.md`](CLAUDE_DEPLOYMENT.md).
8. **SHA-pin every third-party GitHub Action.** Format: `uses: <owner>/<repo>@<full-40-char-SHA>  # vX.Y.Z`. The `# vX.Y.Z` comment is load-bearing — dependabot's github-actions ecosystem regex parses it to know what version is currently pinned. Reject mutable tag references (`@v4`) at PR review — that's the tj-actions/changed-files hijack class. Resolution recipe in [`feedback-ci-hygiene-going-forward`](../.claude/projects/-home-kanban/memory/feedback-ci-hygiene-going-forward.md). SHA-pinning was adopted over mutable tag references after a 2026-05-24 inventory review.
9. **Act vs. ask.** The posture is the user-level `CLAUDE.md` canon (#11, #13, #14). The always-ask hard gate applies here in full and is owned by the user-level `CLAUDE.md` § Always-ask hard gate — **deliberately not enumerated in this repo**: the copy that stood here had drifted narrower than the owner's list, so a session following it under-asked (card#5913).

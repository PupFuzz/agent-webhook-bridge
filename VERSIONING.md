# Versioning policy

How the bridge is versioned, released, and tagged. **The release flow itself is framework-owned** — the coord plugin's `templates/doc-templates/VERSIONING.md` and its `release-pr` skill own the sequence; § Release flow below carries only what is specific to this repo and points at the template for the rest. Mirrors the kanban-board project's process; see [`feedback-git-workflow`](../.claude/projects/-home-kanban/memory/feedback-git-workflow.md) for the operating rule.

## The core rules

1. **Single source of truth for the version:** the [`VERSION`](VERSION) file at the repo root, containing one semver string and a trailing newline. Read it in PHP via `trim(file_get_contents(base_path('VERSION')))`.
2. **The version bump is a release-event artifact, not a PR-event artifact** — the framework template's rule 2, verbatim: *"Version bumps are release-event artifacts, not PR-event artifacts. Feature/docs PRs targeting the integration branch do **not** bump the version or touch release artifacts."* Which branch carries the bump here, and how it reaches `dev`, is § Release flow.
3. **Every release tag `v<version>` corresponds to a `docs/CHANGELOG.md` entry** describing what bundle of merged PRs is in the release. **Enforced at PR time** by [`changelog-gate.yml`](.github/workflows/changelog-gate.yml) since DL-276 — before that it was enforced only by whoever cut the release noticing, and a release cut without its entry published a generated placeholder over the gap.
4. **Tags are created on `main`, not `dev`, by CI.** After the user merges the release PR (`release/v<version>` → `main`), the [`auto-tag-version.yml`](.github/workflows/auto-tag-version.yml) workflow fires on the push to `main`, reads `VERSION`, tags the merge commit `v<VERSION>`, and publishes a GitHub Release from that version's `docs/CHANGELOG.md` section. **Claude does not hand-tag** — the workflow owns it (idempotent; a tag already at a *different* SHA fails the workflow loud, meaning the release PR forgot to bump `VERSION`). The tag SHA equals the merge commit's SHA on `main`.
5. **Back-merge `main` → `dev` after every release** so the branches don't diverge (per [`feedback-auto-backmerge-after-release`](../.claude/projects/-home-kanban/memory/feedback-auto-backmerge-after-release.md)). The user's confirmation that the release PR merged to `main` IS the authorization for the back-merge sync PR — Claude opens it autonomously (no separate ask) and auto-merges on green.

## Branching model

Two long-lived branches: **`main`** (releases only) and **`dev`** (integration). All feature work branches off `dev` and PRs back to `dev`. Only the user merges to `main` (release PRs).

This is the same shape as kanban-board, adopted wholesale.

## Bump sizing

The bridge is pre-1.0, so semver's stability guarantees don't formally apply until v1.0.0 and breaking changes are allowed within a minor (call them out in the changelog). The **effective cadence** — matching the actual tag history (e.g. v0.44.0 feature → v0.43.1/.2/.3 and v0.44.1 fix/refactor patches) — is:

- **Patch** (`x.y.Z+1`) — bug fixes, dep bumps, refactors, docs, internal-only changes with no new user-visible surface.
- **Minor** (`x.Y+1.0`) — new user-visible additions (a new provider adapter, a new CLI flag, a new writeback outcome).
- **Major** (`X+1.0.0`) — reserved for post-1.0 breaking changes to the public surface (classifier interface, config schema, CLI flag removal, a migration needing operator action).

When a release mixes a feature with fixes, lean minor; a fixes/refactors/docs-only release is a patch.

## Release flow

**The sequence itself is framework-owned and is not restated here.** The coord plugin's `templates/doc-templates/VERSIONING.md` states the rule — *"Version bumps are release-event artifacts, not PR-event artifacts. Feature/docs PRs targeting the integration branch do **not** bump the version or touch release artifacts"* (§ The Rule, 2) and *"After the release merges and the tag mints, open a `sync/…-post-<version>` PR carrying the release-bump commits back to the integration branch (merge-commit only; do NOT rebase the sync branch — rebase flattens the merge topology). Back-merge after EACH release; don't batch."* (§ Post-merge) — and the plugin's `release-pr` skill walks it: cut a throwaway `release/vX.Y.Z` branch off the integration branch, put the bump and the CHANGELOG fold on that branch, open **one** PR from it to `main`, and let the back-merge carry both to `dev`.

⛔ **There is no `release/* → dev` release-prep PR, and this doc used to prescribe one.** Two steps here described opening that PR and auto-merging it to `dev`; they stood through six releases without once being executed, and they could not have been — the auto-delete-head-branches setting step 7 warns about would delete the `release/v<version>` branch that step 7's `→ main` PR needs as its head. Roundtable #412 measured zero `release/*` merges into an integration branch anywhere in the fleet and ruled the one-PR flow. Those steps were a local restatement that had drifted from the template, so they are **deleted rather than corrected** — a corrected copy drifts again, which is how they got here (card#8822).

The numbered steps are this repo's instantiation of that flow, carrying only what is local to it: its bump sizing, its declared artifact set, its gates, and its user-merge gate. Policy (per `CLAUDE.md` rule #5 — the ask-before-opening checkpoint is retired): open PRs autonomously; auto-merge dev-targeted on green; only the user merges to main.

1. **Pick the next version.** Read `VERSION`, pick the next semver per the bump-sizing rule above.
2. **Cut the release branch off `dev`.** Name it `release/v<version>`: that spelling is the head this repo's gates expect (`changelog-gate.yml` and `pr-title-lint.yml` exempt `release/*` and nothing else release-shaped), and it stays the PR head all the way to `main` — step 7 owns why it is never `dev`.
3. **Bump `VERSION`** to the new semver.
4. **Update `docs/CHANGELOG.md`.** Move `[Unreleased]` content into a `## [X.Y.Z] - YYYY-MM-DD` heading, then re-seed `[Unreleased]` as empty.

    **After this lands, every branch that was already open owes a relocation.** Its `[Unreleased]` entry is now inside `## [X.Y.Z]`, because the fold moved the heading and not the entry. Merge `dev` into the branch and move the entry back under `[Unreleased]`; do not write a second one. `changelog-gate.yml` fails such a PR and its message names the section to move it out of.

5. **Add the release's `CLAUDE.md` § Recent releases row** (trimming the table back to the last 10, per the doc-retention discipline that section states). Not optional bookkeeping: since DL-279 a release PR that leaves any declared artifact behind hard-fails CI. **[`.release-pr.json`](.release-pr.json)'s `artifacts` array is the authority for the full member set** — read it there; this list is not a second copy of it.
6. Run the pre-PR review loop (CLAUDE.md rule #1) on the release surface.
7. Open the release PR `release/v<version>` → `main` (no ask to open; the user-merge gate in step 9 is the control point). **CRITICAL: the PR head must be the `release/v<version>` branch, NOT `dev` directly.** GitHub's "Automatically delete head branches" repo setting auto-deletes whichever branch is the merged PR's head — if you set head=`dev`, `dev` gets deleted when the user merges. Repo settings can't reliably exclude `dev` on the free plan (branch protection rules require Pro for private repos), so the discipline lives in the branch-naming convention. (The framework template does not state the head-branch shape — only the `release-pr` skill pins it, at `--head "release/vX.Y.Z"` — which is why it is stated here; framework `card#8824` is carrying the sentence into the template.)

    **Card coverage — the verdict is a STDERR line printed at the cut, and its durable home is a comment you post on the BOARD — see below. It was a comment on the release PR until DL-416 closed that home; do not put it there.** `release-pr-body` dry-runs `promote-released-cards` over the release range against the board that `.release-pr.json`'s `.promote` block names — a PRE-MERGE probe of the same board that [`release-promote-cards.yml`](.github/workflows/release-promote-cards.yml) promotes against on the main-push — early enough that a missing card is still a board edit rather than post-tag surgery. ⛔ **It is NOT the same correlation, and a clean line here does NOT predict a green promote there:** the dry-run is handed `--cards` ids derived from commit subjects, while the push path passes an empty `dls` input and `promote-released-cards` matches `dl_number` and the `(#NNN)` → `pr_number` marker, deriving card ids never. In a repo where `card#<id>` is the dominant title form, a clean pre-merge line and a red post-merge promote are compatible states.

    ⛔ **The reading this step carried until DL-402 is DEAD, and it is named here rather than quietly deleted, because a reader who learned it is worse off than one who never saw it.** It described a `## Card coverage` H2 in the generated body and gave a four-way verdict off which variant the body carried — including that a body with **no** such section meant the check DID NOT RUN. Since agent-board-toolkit **DL-224** (card#9248, which reports the framework's PR-body lint redding on that heading) the generator emits no such section at all; the verdict goes to stderr as `release-pr-body: card coverage: …`. Re-derived on this host 2026-09-20: `command -v release-pr-body` resolves into agent-board-toolkit `0.35.1`, whose `card_coverage_report()` prints every line through a `coverage_line()` helper writing to fd 2 and returns **before** printing anything when an input is missing. So **every** release body now lacks the section, three of the old table's four rows described body states the generator can no longer produce, and the absence a reader was told to act on distinguishes nothing.

    **So read the stderr, not the body.** A `card coverage:` line means the check MEASURED, and the line's own words are the verdict — whether the range is clean, which shipped refs have no tracking card, and which have a card carrying no by-ref source (a state this repo is exposed to specifically: `.promote.source` names this repo, so an unsourced card is named and skipped rather than moved — card#8423). That wording is the tool's and is deliberately not enumerated here. **No line at all means it did NOT measure**, and WHICH input it lacked is the tool's to say, not this doc's.

    ⛔ **Read the function's own gates — do NOT look for a block by name.** This step pointed at a `CARD COVERAGE PRECONDITIONS` block above `card_coverage_report()` in `release-pr-body` (agent-board-toolkit card#10039). That block is real, but it landed on the toolkit's integration branch after its last tag and **as of 2026-09-23 was in no tag at all**, so it was absent from the tool this host actually runs — measured that day: `grep -c 'CARD COVERAGE PRECONDITIONS' "$(command -v release-pr-body)"` printed `0` against toolkit `0.35.1`, and `0` against the framework's `templates/release/release-pr-body` mirror. **A pointer at a block BY NAME is a claim about the installed version, and this doc cannot make one** — the release cutter's `PATH` decides it. The function's gates are not version-scoped in that way, so derive them from whatever copy is installed:

    ```sh
    sed -n '/^card_coverage_report()/,/^}/p' "$(command -v release-pr-body)"
    ```

    **Every `return` reached before the first `coverage_line` call is a precondition**, and the identifiers each one tests name the input that was missing — read them off that output rather than off a list kept here, which is a copy of one version's gates and drifts by construction. (Dated observation, not a contract: run against `0.35.1` on 2026-09-23 that span returned early unless a token regex was declared, `.promote.board_id` was set, `KANBAN_WRITEBACK_TOKEN` was exported, and `promote-released-cards` was resolvable. Re-run the command; do not trust that sentence.) The toolkit's `docs/INSTALL.md` §4 is where a consumer learns how to set each key up. Then run `promote-released-cards --dry-run` over the release range yourself before the merge.

    **Record the result ON THE BOARD before step 9's notification — NOT on the release PR.** Stderr scrolls past at the cut and is not an artifact anyone can read back, and the record's whole value is that it is written at the moment the line exists. ⛔ **The test any home must pass is stated here so it cannot be quietly regressed: can a person other than the cutting seat read this back later?** Check a proposed home against that sentence, because the convenient ones fail it — a file under `~/.cache` on the cutting machine is invisible to everyone else (v0.88.0's verdict was parked at `~/.cache/coord/releases/bridge-v0.88.0/pr780-comments-preserved.md`; that was a stopgap and is named here so it is not mistaken for the convention). The tag annotation and the GitHub Release body pass that test and fail a different one — both are installer-facing, which is what closed the home this step used to name.

    ⛔ **That home is CLOSED. Operator ruling, 2026-09-23: release PR bodies AND comments are INSTALLER-FACING ONLY** — coord and process commentary belongs on neither. The v0.88.0 release PR's comments, the card-coverage record among them, were removed on that instruction. DL-402 chose the PR comment; **DL-416 replaces it, and a future edit must not restore it.**

    **So: comment the verdict onto the cards the line names.** Paste the `card coverage:` line(s) verbatim onto each card the release range cites — `kbcard --board bridge comment --task <id> --content-file <path>`, the file form because the line is text you did not write and an inline `$(…)` in it would run in your shell — or, when no line printed, say so, name the input the tool lacked, and record what your hand-run `--dry-run` said. **A correlation gap has no card to comment on, and that is the point: mint one.** A shipped ref with no tracking card, or a card carrying no by-ref source, becomes a card on this repo's board carrying the verdict line, before the merge — which is the board edit this pre-merge probe exists to still make cheap. The board is readable by any seat, it is the same surface step 11's post-merge promote writes to, and no body generation or `pr-body-lint` step can strike it.

    ⛔ **It is a convention, not a gate: nothing reds when the verdict is not recorded**, so a release carrying no record is not a pass — it is a release whose coverage result was never written down. It is also a PRE-merge record of the range as of the moment it was written, and it quotes the DRY-RUN; step 11's post-merge `release-promote-cards` remains the real correlation and can still red. Skipping it is what strands a card: the post-merge promote reports a cardless ref after the tag has landed, where the fix is board surgery instead of a commit (DL-165 / DL-172 are what that failure looks like from the other end).
8. Wait for CI to complete + pass on the release → main PR, per `CLAUDE.md` standing rule #5 — it owns what must be green and how to read the list (card#5575; deliberately not restated here).
9. **Notify user it's ready to merge.** Claude does NOT run `gh pr merge` against a `main`-targeted PR regardless of CI state.
    **Merge method: "Create a merge commit" — NEVER squash, never rebase.** `dev` and `main` must
    share history, or the post-release back-merge (step 12) replays the whole release as fresh
    commits and every subsequent release diff is wrong. This doc owns that rule: the PR-body
    standard (`coord:release-pr` § PR body) puts process warnings OUT of the body and into the
    repo's own release doc, so a reader looking for it comes HERE. Do not restate it in a PR body.
10. **After user merges to `main` and confirms the merge to Claude:** that confirmation is the standing authorization for the back-merge sync PR — Claude does NOT ask again. (The tag + GitHub Release are minted automatically by `auto-tag-version.yml`; Claude does not hand-tag.)
11. `auto-tag-version.yml` (on the push to `main`) tags the merge commit `v<VERSION>` and publishes the GitHub Release from the `docs/CHANGELOG.md` section — automatically, no Claude action. (Fallback only: if the workflow is ever absent, the user's merge confirmation is the standing authorization to tag manually.)

    **[`release-promote-cards.yml`](.github/workflows/release-promote-cards.yml) fires on the same push, as an INDEPENDENT run with no `needs:` between them — so it waits for that tag before it moves a card (card#8286).** The two workflows race, promote wins it on every release, and until the gate landed the board was stamped "Released to main" against a tag that did not exist yet; where the tag never arrives, that assertion is simply false and nothing corrects it. A step ahead of the promote step — the toolkit's SHA-pinned `release-tag-check` — waits for `v<VERSION>` on the remote and refuses to promote if it never appears. **A push to `main` that does not move `VERSION` is not gated at all** — the gate classifies the pushed range and asserts nothing on a non-release.

    ⚠ **What a red `release-promote-cards` run means for the operator: go look at whether the tag exists — NOT that a board write failed.** Three refusals with three different meanings: the tag is absent past the tool's bound (check `auto-tag-version.yml`'s run for this push), the tag exists at a **different** commit (two merges claimed one version — the earlier release PR forgot to bump `VERSION`; refused immediately, since waiting cannot move a tag), or the remote could not be **read**, in which case the tag is unmeasured rather than absent and the message says so. **The refusal is loud in Actions and silent on the board** — the cards simply stay in Shipped-to-Dev, there is no "release refused" signal on the board itself, so watch the workflow run and not the column. Recovery for the first case is to re-run the `auto-tag` job and then re-run this one — a re-run classifies the same range, so a card already at Released is skipped by the `shipped-stage-ids` source-stage guard rather than moved twice.
12. **Back-merge `main` → `dev`** — the framework's Rule E, whose procedure the `release-pr` skill's § Back-merge sync PR owns; here the branch is `sync/main-to-dev-post-v<version>`. Claude opens it and auto-merges on green — no additional ask, the user's main-merge confirmation covered it (core rule 5) — and it is what carries the bump, the fold, and any commit the user made directly on `main` (release-PR metadata) back to `dev`.

    ⛔ **Merge it with `gh pr merge <N> --merge --delete-branch` — never `--squash`, and never `solo-self-merge`, which squashes** (`CLAUDE_AGENTBOARD.md` § self-merge rules says the same thing about the same PR; step 9 above owns the merge-method rule for this repo) — **then run this and READ it:**

    ```sh
    git fetch origin dev && git rev-list --parents -n1 origin/dev | wc -w
    ```

    **It must print `3`** — the commit plus two parents. Run it while the back-merge is still `dev`'s tip, i.e. straight after the merge and before anything else lands; later it measures whatever commit is on top instead. **`2` means the back-merge was SQUASHED, and the consequence is not cosmetic:** `main`'s release commits never become ancestors of `dev`, so the next release's merge base falls back to before the last release and **the next release PR opens `CONFLICTING`** — and a dirty PR builds no merge ref, so its `pull_request` workflows produce **zero runs, forever**. That is an *absent* CI signal, not a red one, which is why it is not noticed at the cut. A `2` is to be fixed before the next cut, not discovered at one.

    ⚠ **A squash here is a CHOICE at the merge step, not the platform's doing — do not read it as a restriction.** `dev`'s ruleset pins `allowed_merge_methods: ["squash"]`, but its bypass grants the repo-admin role `bypass_mode: always`, so the merge-commit method is offered and has been taken. Measured per back-merge with `git rev-list --parents -n1 <sha> | wc -w`: PR #689 (post-v0.83.0, `319b73d`) → `3`, PR #700 (post-v0.84.0, `693c656`) → `3`, **PR #760 (post-v0.87.0, `e8ffb9c`) → `2`** — the squashed one, and v0.88.0's release PR is the one that opened dirty. ⛔ **Do not propose a ruleset change over this:** the single-admin bypass is a standing operator ruling and is not to be re-raised.

    ⭐ **Land it before the next merge to `dev`.** Until it does, `dev` still carries the un-drained `[Unreleased]` while `main` carries the folded one, so every branch open across that window acquires the pre-fold state § What CI enforces describes below — a window measured here as minutes wide and still wide enough to catch a PR. **The bound on that window, and the guard for it, are framework-owned and this repo keeps no copy of either:** roundtable #412 ruled it and it is being built framework-side as `card#8824`.

## What CI enforces about the CHANGELOG and the declared release artifacts (DL-276, DL-279)

**Two** workflows read the release docs **before** a merge, on `pull_request`. They compose — neither replaces the other, and they share no code:

- [`changelog-gate.yml`](.github/workflows/changelog-gate.yml) (DL-276) owns `docs/CHANGELOG.md`: that a version bump carries its `## [<VERSION>]` section, that the section fits GitHub's release-body limit (the assertion nothing else makes), and that every PR touching an in-scope path is named in `[Unreleased]` (the scope table below owns the member list).
- [`release-artifacts-gate.yml`](.github/workflows/release-artifacts-gate.yml) (DL-279) owns the must-move-together SET: that **every** member declared in [`.release-pr.json`](.release-pr.json)'s `artifacts` array moved in the release PR's own changes, still exists at head, and agrees with the version being shipped. **That array is the authority for the member list** — the gate reads the declaration instead of naming files, so a new member is guarded by declaring it. It says nothing about the release-body limit.

`changelog-gate.yml`'s two assertions:

| When it fires | What it requires | Why here and not post-merge |
| --- | --- | --- |
| The PR changes `VERSION` | `docs/CHANGELOG.md` carries a `## [<VERSION>]` section, **and** that section is within GitHub's 125,000-byte release-body limit | Post-merge the tag has already landed. A missing section published a placeholder; an oversize one left the release tagged and **unpublished** (v0.72.0, HTTP 422) |
| The PR changes `app/`, `bin/`, `.github/workflows/`, `.github/actions/`, `.release-pr.json`, `phpstan-laravel.neon`, `pint.json`, `phpunit.xml`, `composer.json`, `composer.lock`, or `.env.example` (every member with no trailing `/` is matched as a whole root path, not a prefix — `config/pint.json` and `phpunit.xml.dist` are out) | The `[Unreleased]` section names the PR title's `card#`/`DL-` token — or, for a PR with no such token, `[Unreleased]` changed at all | Nothing else reads the changelog between releases, so an omission is invisible until one is cut. 25 of 56 tokened commits reached v0.72.0 undocumented this way. `.github/workflows/` joined the scope on card#6056 (DL-280): what CI accepts or rejects is shipped behaviour for a contributor, and the DL-279 gate adoption — a change to what CI accepts on every release PR — was itself structurally exempt. **card#6100 (DL-282) then NARROWED — did not close — the gap DL-280 disclosed between the path scope and that criterion**: five more files a CI step reads joined the scope, because widening to two of the five and not the rest would re-mint the *guard reads a proper subset* shape one directory down. **card#6137 (DL-288) then moved DL-282's own three disclosed CI-half gaps across** — `composer.json` (its `require-dev` pins the analysers the SQLite job runs out of `vendor/bin`), `composer.lock` (`composer audit --locked` reads it as that gate's rule input) and `.env.example` (copied to `.env` for both test jobs) — which discharges that disclosure without closing the CI half. **DL-288 newly discloses a CI-half gap of its own, on the same mechanism:** the reference channel server's `examples/channel-servers/package.json` and `package-lock.json`, which `channel-server-supply-chain.yml` reads as rule input — `npm ci --ignore-scripts` fails the PR on manifest/lock drift, `npm audit --audit-level=high` reads the lockfile, and its version-bump job reads the manifest's `version` — with a second `npm ci` against the same lockfile in `provision-tools-python.yml`. card#6137 owns the disposition; widening to reach that pair is a change to what CI rejects and needs its own operator ruling. This list is not claimed to exhaust that criterion. `config/`, `routes/` and `database/migrations/` still sit outside the software half as a bound inherited from DL-276. `phpunit.xml`'s test-fixture `<php><env>` block is inside the scope as an accepted coarse-predicate bound (DL-282) |

**"The PR changes …" in both rows means the MERGE's own delta** — `git diff --name-only "$BASE" HEAD`, where `HEAD` is the `refs/pull/<n>/merge` commit `actions/checkout` hands a `pull_request` job and `$BASE` is that merge's own first parent (`bin/pr-base-snapshot.sh`; card#8527, [DL-295](CLAUDE_DECISIONS.md) amendment): the files this PR would change ON THE BASE if it merged now. It is **not** the range between the base tip and the branch tip — a branch not up to date with its base carries the base's own post-fork commits there, which made both verdicts a function of what merged on `dev` while the branch was open (card#8441's finding) — and not the branch-tip merge-base (`...`) range either: a change the base already carries identically is inside that range and lands nothing, so no entry is owed for it. Merge delta ⊆ merge-base range ⊆ base-tip-vs-branch-tip range, so the current spelling can only stop either gate firing, never start it.

Exempt branches — **the `[Unreleased]`-entry assertion only**, same set as `pr-title-lint.yml`: `dependabot/*`, `release/*`, `sync/*`, `revert-*`. The `VERSION` assertion exempts no branch (a `release/*` PR is precisely what it must check; it is classified by the version MOVING, not by the base ref, so the release branch's two PRs are both covered without naming either). A docs-only or test-only PR is exempt from the `[Unreleased]`-entry assertion by the path scope, not by a carve-out. `release-artifacts-gate.yml` likewise exempts nothing: a non-release PR is skipped by version VALUE, so it never needs a branch name.

**A branch cut BEFORE a release fold is a distinct failure with the opposite remedy, and the gate says which one it is (card#8339).** The fold in step 4 above renames `## [Unreleased]` to `## [X.Y.Z]` and opens a fresh empty one above it; a branch open across that keeps its entry under the heading git now reads as `[X.Y.Z]`, with no conflict and no author error, so it merges into a **released** section that then claims work that release did not ship. The `[Unreleased]`-entry assertion fires — correctly — and would once have answered *"add an [Unreleased] entry"*, which files a **second** entry and leaves the first corrupting the released section. It now reads the merged changelog (`actions/checkout` gives the gate `refs/pull/<n>/merge`), finds the released section carrying a line **this branch introduced**, and — **only when it can ASSERT that the section was cut while this branch was open, never inferring it from where the line sits** — names it: *"your entry is under `[X.Y.Z]` because the branch predates the fold — move it under `[Unreleased]`"*. Other shapes that put a branch line under a released heading fail that predicate and get the message the gate always printed. **This is a diagnostic only — the verdict is byte-for-byte what it was.** [DL-329](CLAUDE_DECISIONS.md) owns the predicate, its third leg, and the single copy of its residual list; this paragraph deliberately does not restate any of them.

Both of that gate's assertions and the release publisher extract sections through the single `bin/changelog-section.py`, so the gate measures the body the publisher would actually ship. [`auto-tag-version.yml`](.github/workflows/auto-tag-version.yml) **stays fail-soft on a missing section by design** — failing there would leave a merged release untagged — but an oversize section is now truncated to whole lines with a pointer to the full entry at the tag, rather than failing the publish.

## Anti-patterns

- **Don't tag a release before doc-sync.** The CHANGELOG entry must land in the same commit as the version bump (typically the same release PR).
- **Don't bump the version on a regular feature PR.** Version bumps belong to release events.
- **Don't reuse a tag.** Tags are immutable; if a release is broken, ship `vX.Y.Z+1` not "v0.1.0-fixed".
- **Don't tag `dev`.** Only `main` gets tags. `dev` is a moving integration target.
- **Don't PR `dev` directly to `main`.** Use a disposable `release/v<version>` branch as the PR head. If `dev` is the PR head and the user merges with auto-delete-head-branches enabled, `dev` is deleted. (The discipline lives in the branch-naming convention because of a prior incident where `dev` was deleted this way.)

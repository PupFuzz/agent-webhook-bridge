# Config schema (current-state reference)

The **what**: every configuration key the bridge reads, its type, default, and what `bridge:check` reports for a bad value — **fails closed** (throws/5xx/non-zero), **warns**, or reports **`unvalidated`** when a leg could not measure at all (the third value has been in the vocabulary since DL-236; describing it as a binary was wrong from that release onward). The **why** of each choice lives in [`../CLAUDE_DECISIONS.md`](../CLAUDE_DECISIONS.md) (the `DL-NNN` log); this file is the flat reference so you don't have to reconstruct the schema by reading DL-002 + 005 + 006 + 007 + 008 + 010 + 011 + 014 as deltas. (B-11.)

There are three configuration surfaces:

1. **Per-install** — Laravel `.env` → `config/bridge.php`. Same for every agent on one install.
2. **Per-agent** — `<config_dir>/<agent>.yml`. One file per agent; the **filename is the agent name**.
3. **Secrets / state** — files under `<secret_dir>` / `<state_dir>`, not committed.

## 1. Per-install (`.env` / `config/bridge.php`)

| Env var | Type | Default | Notes / fail mode |
|---|---|---|---|
| `BRIDGE_DIR` | abs path | — | Base dir for per-agent YAMLs, `shared-identities.json`, secrets, tokens, and `state/`. `config_dir` + `secret_dir` default to it. |
| `BRIDGE_CONFIG_DIR` | abs path | `BRIDGE_DIR` | Override only when config lives elsewhere. Missing/not-a-dir → `bridge:check` **fails**; dispatch reads it per request. Group/world-accessible → **warn** (DL-014). |
| `BRIDGE_SECRET_DIR` | abs path | `BRIDGE_DIR` | Holds HMAC secrets + tokens. Not set / not absolute → `bridge:check` **fails**. Group/world-accessible → **warn** (DL-014). Set to a path that does not exist → **warn**; set to a path this process cannot traverse to → **`unvalidated`** (DL-264 — the checking process commonly runs as a different OS user, and "absent" is not a conclusion it is entitled to draw); set to a path that EXISTS but is **not a directory** → **fails** (DL-265 — every secret and token resolves underneath it, so not one can be opened and no webhook can be verified; its mode is deliberately NOT reported, because `chmod 700` on a regular file is advice that would make things worse). These are reported only on a **split layout** (`secret_dir` ≠ `config_dir`); when the two are the same path the config-dir row above reports it, and the perms leg stays silent to avoid a duplicate line. |
| `BRIDGE_INSTALL_SUFFIX` | string | `''` | `-prod` / `-dev` crosstalk marker. `InstallGuard` requires the DB name to **contain** the marker with `-`→`_` (i.e. `_prod` / `_dev`, as a substring) — else the receiver **5xx**s and `bridge:check` **fails** (DL-001). |
| `BRIDGE_RECEIVER_BASE_URL` | http(s) URL | — | This bridge's public webhook URL (used by `bridge:provision`). Malformed → `bridge:check` **fails**. |
| `BRIDGE_KANBAN_API_BASE_URL` | http(s) URL | — | kanban API base. Malformed → `bridge:check` **fails**. |
| `BRIDGE_GITHUB_API_BASE_URL` | http(s) URL | `https://api.github.com` | Only relevant if a github adapter calls the API. |
| `BRIDGE_GITHUB_TOKEN_PATH` | abs path | — | `bridge:reconcile` GitHub read token (DL-184). Authoritative when set: a missing/blank/insecure file **fails loud** with no store/env fallback. Absent → the conventional `<secret_dir>/github/token`, then store-native, then `GH_TOKEN`. |
| `BRIDGE_GITHUB_CREDENTIAL_HELPER` | helper name \| abs path \| `''` | `git-credential-coord` | `bridge:reconcile` store-native token leg (DL-185): resolves a **per-repo** PAT from the coordination store's `[git-credential-map]` via this helper (git wire-format). Needs `HOME`/`COORD_CREDENTIALS` in the reconcile env to locate the store. |
| `BRIDGE_STATE_DIR` | abs path | `<config_dir>/state` | `inbox*.jsonl` / seen cursors / handler logs. Point OUTSIDE the 0700 config dir for cross-user inbox reads. |
| `BRIDGE_INBOX_LAYOUT` | `shared` \| `per-agent` \| `both` | `shared` | Where staged lines land. Invalid → `bridge:check` + dispatch **fail closed**. |
| `BRIDGE_DEFAULT_AGENT` | agent name | — | Bare `bridge:inbox` surfaces this agent. Unknown name → `bridge:check` **warns**. |
| `BRIDGE_INBOX_FILE_MODE` | octal string | `0640` | Mode applied to per-agent **inbox** files (cross-user read). Seen-cursor files stay install-user-owned (default umask). |
| `BRIDGE_INBOX_GROUP` | group name | — | Group on per-agent inbox files. **Requires `per-agent` layout** (else `bridge:check` + dispatch **fail closed** — a group-readable shared inbox would leak every agent's intents, DL-006). |
| `BRIDGE_MAX_BODY_BYTES` | int | `262144` (256 KB) | Envelope size cap; oversize → `413` before HMAC work. |
| `BRIDGE_RETENTION_ENABLED` | bool | **`true`** | Prune the append-only stores after each delivery (DL-199), from a terminating callback so the response is already sent. **On by default — an upgrade starts pruning without operator action** (a default nobody sets is why DL-012's cron never ran). `false` ⇒ nothing prunes unless you schedule `bridge:prune`. `bridge:check` **warns** when disabled. |
| `BRIDGE_RETENTION_INTERVAL` | int (seconds) | `86400` | Gap between passes **once the store is drained**. While a backlog remains the gate keeps draining on successive deliveries instead of waiting this out (each pass is still capped by `batch`). `< 1` ⇒ prunes **nothing** + `bridge:check` warns. |
| `BRIDGE_RETENTION_OLDER_THAN` | `Nd` \| `N` \| `''` | `30d` | Delete `webhook_events` (cascading `agent_dispatches`) + trim `inbox*.jsonl` older than this. Same 1–36500 guard as `--older-than`. Unparseable ⇒ prunes **nothing** (never falls back to a default cutoff — that would delete on a typo) + `bridge:check` warns. Empty ⇒ this (row) leg off, and **`bridge:check` warns** naming how many rows are retained (card#8374) — rows and their dispatches are then never deleted. ⚠ **That warning is emitted only when the store could be MEASURED**: the row count is the warning's own evidence, so a run whose store read threw reports `retention: could NOT measure …` (`unvalidated`) and emits no leg warning at all. ⚠ **Since DL-315 an empty value is a LIVE posture, not an inert one**: with both windows empty this install was reported `MISCONFIGURED` and pruned nothing, and the payload default below (now `7d`) makes the same `.env` usable — so the payload leg runs. Upgrade note: `CLAUDE_DEPLOYMENT.md` § *Retention config (DL-199)*. |
| `BRIDGE_RETENTION_NULL_PAYLOADS_OLDER_THAN` | `Nd` \| `N` \| `''` | **`7d`** | Null `webhook_events.payload` past the replay window, keeping the row (its `delivery_id` dedup gate + audit metadata). Use a value **smaller** than `older_than`. **On by default — an upgrade starts nulling payloads without operator action** (DL-315; payloads were ~95% of the store's bytes on both installs that measured it). ⚠ **This IS the replay window, not a space setting**: `bridge:replay` **REFUSES** an event whose payload is nulled — it cannot reconstruct it, and dispatching an empty payload in its place would stage a fabricated intent — and `bridge:stats` counts those errored rows under `errored (NOT replayable …)`. Set it to your detection latency + response time. ⛔ **There is no grace period:** the retention gate's marker is a *cache* key, so the first inbound webhook after deploy runs a pass and keeps draining while a backlog remains. Empty ⇒ leg off, and **`bridge:check` warns naming the bytes of payload the install is then holding** (card#8374) — a green `retention: on (…)` beside a switched-off nulling leg is the state that made 894 MB invisible. ⚠ **That warning is emitted only when the store could be MEASURED** — the bytes ARE the warning, so a run whose store read threw reports `unvalidated` and emits no leg warning at all. To opt out or widen it, set the value **before** the upgrade **and re-run `php artisan config:cache`** — a `.env` edit is inert under a cached config. Unparseable ⇒ prunes **nothing** + `bridge:check` warns. |
| `BRIDGE_RETENTION_BATCH` | int | `500` | Max rows one pass touches **per leg** — the bound that keeps a pass to milliseconds of FPM-worker time instead of a 20k-row `DELETE`. Deleted oldest-first. `< 1` ⇒ prunes **nothing** + `bridge:check` warns. Does **not** bound the inbox trim (a jsonl rewrite is whole-file; the cost is paid once). |
| `BRIDGE_STANDUP_ENABLED` | bool | **`false`** | Push the PM standup digest (DL-306) after a delivery, from the same terminating callback retention uses. **Off by default** — unlike retention, a pass makes OUTBOUND calls (a board read per mapped board, then the channel push), so it is opt-in per install. Disabled ⇒ no callback is registered at all, and `bridge:check`'s `standup.posture` leg says **nothing** (an install that never wanted a digest is not failing by not pushing one). Enabled, that leg reports the posture and — the reason it exists (card#8683 / DL-345) — surfaces a pass that **THREW**: the gate backs off a full `interval` after one, so a seat whose channel server is down just stops receiving digests. It never `fail`s, so it does not move the command's exit code. |
| `BRIDGE_STANDUP_AGENT` | agent name | — | The seat the digest is pushed to, by `<agent>.yml` filename; its own `channel` block is the endpoint and its `channel.auth.token_path` the bearer (the push runs through the registered `channel_push` handler). **There is no default recipient.** Unset/blank, a non-string (a bare `true` in `.env` reads as a bool), or a value that is not a bare `<agent>.yml` name (`../x`, `.hidden`) ⇒ the digest is **refused** — the name is concatenated into a `<config_dir>/<agent>.yml` path, so a traversal would push this install's fleet snapshot at whatever channel a YAML outside the config dir names. Refusals push **nothing** and warn once per day, never per delivery. |
| `BRIDGE_STANDUP_INTERVAL` | int (seconds) | `86400` | Gap between passes. ⚠ **A delivery cadence, not a wall clock:** the pass runs on the first inbound webhook AFTER this elapses, so a silent install pushes nothing and a quiet stretch delays one — run `bridge:standup` from your own scheduler if you need a wall clock (the two are idempotent). `< 1` ⇒ pushes **nothing** + warns. |
| `BRIDGE_JOBS_ENABLED` | bool | `true` | The periodic-job registry (DL-325) as a whole, evaluated off the inbound webhook from the same terminating callback retention uses. **On by default and INERT with no rows** — an install that adds nothing behaves exactly as before, at the cost of one indexed query per `min_pass_interval` on delivery. `false` ⇒ no callback is registered at all, and `bridge:tick` runs no pass either; `bridge:check` **warns** if the registry is disabled while instances exist, because `bridge:jobs` would still list a periodic population that nothing runs. |
| `BRIDGE_JOBS_MIN_PASS_INTERVAL` | int (seconds) | `60` | Floor between scheduler passes, **shared by BOTH ingresses** — the event gate is evaluated on every delivery, so without it a busy install would query the registry once per webhook. A 5/10/15-minute-class tick is never affected by it. Each instance's own `interval_s` is what decides when that job is due; this only bounds how often the registry is consulted. ⚠ **A value that is not a positive integer is REFUSED, not clamped** — `< 1` (which is what a non-numeric value casts to) means NO pass runs on either ingress until it is fixed, `bridge:check`'s `jobs.posture` leg **fails** naming the key, and `bridge:tick` exits non-zero. Clamping to 1 would have turned an intended `sixty` into a **one-second** floor — a registry pass on every delivery, on the path DL-001's latency bet is spent — and said nothing; the same direction retention fails in (an unparseable window prunes nothing rather than falling back to a default cutoff). |
| `BRIDGE_JOBS_MAX_PER_PASS` | int | `3` | Max instances one pass runs, **oldest-due first** — the DL-199 bound, and the reason a registry with 50 due jobs drains across passes instead of becoming one long after-response callback. ⚠ **Refused, not clamped**, outside `1…1000` — same handling and same reporting as `BRIDGE_JOBS_MIN_PASS_INTERVAL` above. The ceiling exists because `(int)` on a 20-digit string saturates to `PHP_INT_MAX`, which would make one after-response callback try to run the whole registry inside an FPM worker. |
| `BRIDGE_JOBS_ARMED_MUTATORS` | comma-sep handler names | `''` | ⭐ **The governance gate, and the only ask-the-operator knob in the subsystem.** A job handler declaring the state-mutating capability is **inert** until named here: the insert is refused, and if it was armed when the row was created and disarmed since, the run is refused too — loudly, with the instance recording `refused` and `bridge:check` failing. Read-and-alert handlers (staleness checks, wakes, watches, cleanups) need **no** entry, which is what makes inserting instances of them free. Empty ⇒ no state-mutating handler can run on this install. |
| `BRIDGE_JOBS_TICK_EXPECTED_EVERY` | int (seconds) | *(unset)* | ⭐ **The tick adoption knob AND the death-is-the-alarm horizon.** Set it to the interval of the one crontab line you added (`600` for a ten-minute line) — see `docs/periodic-jobs.md`. The bridge records the last tick it received and judges freshness against **this number**, never a fleet-wide constant, because only this install knows what its crontab says. **Unset (the default) ⇒ the tick was not adopted, and its absence is NEVER reported as a fault** — `bridge:jobs --assert-tick` exits 0 and the `jobs.posture` leg says nothing. An **absent** record is reported as `unmeasured`, never as death; a record with no declared horizon gets an age and **no verdict**. ⚠ **A value that is not a positive integer does NOT arm the alarm** — `env()` reads a bare `true` as a bool and `ten` as a string, and either would otherwise read as *not adopted*, i.e. identical to an install that never wanted a tick. `bridge:check`'s `jobs.posture` leg **warns** on an unreadable declaration for exactly that reason, because it is the only place an operator who armed it wrongly finds out. ⚠ Inert under `config:cache` until the cache is rebuilt. |
| `BRIDGE_COORD_CONFIG_PATH` | abs path | falls back to ambient `COORD_CONFIG` | Per-install override for the coordination config path. Two installs on one host (`-prod` / `-dev`) share one ambient `$COORD_CONFIG` — set this in that install's `.env` to point them at different coordination projects. **This leg is the cache-safe one**: it resolves through `config/bridge.php`, so it survives `php artisan optimize`. When unset, `bridge:check` falls back to the ambient `$COORD_CONFIG` read live via `getenv()` (see below). Same CLI-only/never-fail semantics as `COORD_CONFIG`. |
| `COORD_CONFIG` | abs path | — | Fallback for the above: the coordination project's `coordination.config.json`. **Deliberately NOT resolved through `config/bridge.php`** — it is read at the `bridge:check` read-site (see below). **Read ONLY by `bridge:check`**, for the DL-200 `move_coord_cards` cross-config terminal compare (resolves that board's `terminal_columns` and compares against `coord_card_terminal_stage_id`). Note this is the **only** non-`BRIDGE_*` env the bridge reads — the name is the framework's, deliberately reused so an operator's existing shell already sets it. **CLI-only by design:** `bridge:check` runs with the operator's environment; the receiver runs under PHP-FPM, which does **not** carry it — so nothing on the request path may read it (a request path bound to an absent file fails silently in the one process nobody watches). **Read live via `getenv()` at the check, NOT baked into `config/bridge.php`** — `php artisan optimize` (the documented deploy step) caches config and would freeze this to whatever the *deploying* shell had, usually nothing, making the compare report CANNOT-VERIFY forever. If you cache config AND want a fixed path regardless of the invoking shell, set `BRIDGE_COORD_CONFIG_PATH` in `.env` (that leg IS cache-safe). Unset/absent/malformed ⇒ the compare reports **CANNOT-VERIFY** (never agreement); it **never fails** `bridge:check`. |
| `BRIDGE_BOARD_TOOLS_CLIENT_HALF_TTL` | int (seconds) | `604800` (7 days) | **DL-313.** How old an agent's last **successful** board-tools call may be and still read as CURRENT in `bridge:check`'s `board_tools.client_half` leg. **A display threshold and nothing else** — the leg prints the AGE either way (*"last successful board-tools call was 3h ago, over ssh"*), so an operator judges the number rather than a boolean; the window only stops an ancient stamp reading as current. **Within it ⇒ `ok`; past it, or with no record at all ⇒ `unvalidated` — never `warn`, never `fail`, and no exit code moves.** ⛔ **A fresh record reports the CALL, not the CALLER:** `bridge:check --probe-tools`, `provision-board-tools.py --self-cert` and a hand-run `bridge:tools-call --agent=X` on the bridge host stamp the row indistinguishably from the seat's own call — and the runbook's verify step (`docs/board-tools.md` § 6) is one of them, one step BEFORE the channel server is restarted — so the `ok` line claims the door opened for that agent and no more, and says so in its own text. ⭐ **DL-316 splits that `ok` into two LINES at one severity:** a call whose SERVING PROCESS had the shape of the pinned, pty-less ssh forced command reports `client half REPORTED **THROUGH THE SSH DOOR**` and enumerates what that rules out; an http call, a hand-run, and **every row written before that migration** keep the line above word for word. ⚠ It still does not name the seat, and the line says so in its own text. **The predicate, what it establishes, and the two things it does NOT are owned by `app/Bridge/Tools/CallProvenance.php`'s class docblock — read them there; this table entry deliberately does not restate them, because the first cut of the feature carried eleven hand-maintained restatements and the rule underneath them was measured wrong.** ⛔ **UNREPORTED is not evidence the seat is unwired:** the bridge may not read the seat's own keypair or `.mcp.json` (an account may only read its own files), so a never-wired seat and an idle one are one absence here and the remedy is to **ask the seat for one call**, not to re-provision it. `< 1` ⇒ the shipped 7-day default is used rather than obeyed (a `0` would stale every stamp the instant it was written, with the leg's own text blaming the seat). |
| `BRIDGE_SPAWN_ENABLED` | bool | `false` | Registers the `spawn_detached` handler. Off ⇒ a `spawn_detached` target is a best-effort note, never an execution (DL-011). |
| `BRIDGE_SPAWN_ALLOWLIST` | comma-sep abs paths | `''` | `cmd[0]` must be in it. Empty ⇒ nothing runs. **Allowlist fixed-purpose wrappers, never interpreters** (DL-011). |
| `BRIDGE_SPAWN_SETSID_PATH` | abs path | _(auto)_ | Absolute path to the `setsid` launcher. Unset ⇒ auto-detect (`/usr/bin/setsid`, `/bin/setsid`). Pinned absolute so a payload `env` PATH can't redirect which `setsid` runs (DL-037); fail-closed if none is found. |
| `BRIDGE_CHANNEL_ALLOWED_SOCKET_DIR` | abs path | — | Prefix a **classifier-supplied** `channel_push` socket must sit under; unset ⇒ classifier sockets **refused** (DL-014). Agent-config sockets exempt. |

DB connection (`DB_CONNECTION` / `DB_*`) and `APP_*` are standard Laravel. The DB password lives in `.env` (`DB_PASSWORD`), never in the YAMLs.

## 2. Per-agent YAML (`<config_dir>/<agent>.yml`)

The **filename** (minus `.yml`) is the agent's canonical name and its echo "self" — there is **no `identity.self`** (DL-007). Malformed YAML throws at load → **5xx** (fail-closed; kanban-board holds + redelivers). `chmod 600` the file.

### `identity:` (optional mapping) — the agent's own immutable upstream ids
| Key | Type | Default | Notes |
|---|---|---|---|
| `kanban_user_id` | int | `null` | The agent's kanban `user_id`. Auto-seeded into self echo-suppression. |
| `github_user_id` | int | `null` | The agent's immutable GitHub `sender.id`. Auto-seeded into self echo. |
| `github_login` | string | `null` | **Display-only label** — never a matching key (renameable; DL-002). A stale value logs a one-line drift warning. |

Recognition keys on the numeric ids only; the agent never hand-lists its own id for echo (auto-seeded, DL-007). Modelled by `IdentityConfig` (DL-017).

### `subscriptions:` (expected list — an agent with none receives nothing) — which provider scopes this agent receives
Each entry:
| Key | Type | Default | Notes |
|---|---|---|---|
| `provider` | `kanban` \| `github` | — | Must have an adapter (`bridge:check` **fails** on an unknown provider, DL-015). |
| `scopes` | list | — | kanban board ids (`[5]`) / GitHub `org/repo` slugs. A scope failing `ScopeId` validation is rejected (it's the path-traversal boundary). |
| `event_filter` | list | `[]` (all) | e.g. `["task.*","comment.*"]`. |

Non-array `subscriptions`, or an entry that isn't a mapping, throws at load. Only `kanban` is API-provisionable (`bridge:provision` skips github with a non-zero exit).

### `echo_suppression:` (optional) — OTHER agents only (self is auto-seeded)
| Key | Type | Default | Notes |
|---|---|---|---|
| `treat_as_echo` | list of agent names | `[]` | Other agents' writes to silently skip (by name). |
| `treat_as_echo_ids` | list of raw ids | `[]` | Extra raw provider ids to skip (rarely needed; self ids are auto-seeded). |
| `treat_as_signal` | list of agent names | `[]` | If non-empty, **only** these agents' writes are signal. **Fail-closed:** a name with no matching `<name>.yml` throws at **preflight (`bridge:check`) / first dispatch** (5xx), not at YAML load (DL-007 — `SignalAllowlist`). |

### `classifier:` (optional)
| Key | Type | Default | Notes |
|---|---|---|---|
| `class` | FQCN | `App\Bridge\Classifiers\InboxOnlyClassifier` | Must be resolvable + implement `Classifier`; `bridge:check` resolves it so a typo **fails** at preflight instead of a dispatch-time 5xx. |
| `config` | mapping | `{}` | Typed parameters for a **config-driven classifier** (`ClassifierConfig`), so a shared reference classifier is parameterized without hardcoding per-project specifics. Absent ⇒ all-defaults (back-compat). A present non-mapping — or a malformed key below — **throws** (fail-closed, like the rest of the config). Read by a classifier via `$ctx->agent->classifierConfig`. |

#### `classifier.config:` keys
| Key | Type | Default | Notes |
|---|---|---|---|
| `scope_author_map` | mapping | `{}` | `scope_id` (repo) ⇒ the sole author-agent on that repo — the primary attribution path for a **label-less** impl event (falls back to the `from:`/`FROM:` line). Keys lowercased for case-insensitive scope matching; a non-string key/value **throws**. **Under a shared upstream identity (DL-002) it is the only attribution path that survives a non-authoring action** (DL-252): its premise is that one agent does *everything* on that repo, so it names the ACTOR of a `reopened`/`closed`/… where no label or body can. (An account the registry resolves — declared in some agent's `identity`, not in `shared-identities.json` — is named on every action before this map is consulted, so an install with no shared account never needs it for that.) Setting it for a repo several agents post on therefore reports the wrong agent as the actor of every event there — a `from:`-label repo must leave it unset. |
| `families` | list<string> | `[]` (classifier default) | The event families a config-driven classifier runs (its config-gated pipeline). Lowercased; a blank entry **throws**. Recognized by `CoordinationClassifier`: `coord-message` (GitHub coordination messages), `impl-ci-wake` (push→release-branch + CI wake), `kanban-triage` (wake the triage owner on a human-filed untriaged card — DL-168). An unknown family is ignored (forward-compat). Empty ⇒ the classifier's own default (`CoordinationClassifier` → `[coord-message]`; the `KanbanTriageClassifier` shim → `[kanban-triage]`). |
| `impl_repos` | list<string> | `[]` (all subscribed) | **`impl-ci-wake` family.** Gate the impl wake (push→release-branch / `workflow_run` CI) to a repo subset — the family fires only when the event's `scope_id` is in this list. Lowercased for case-insensitive matching. Empty/absent ⇒ every subscribed repo wakes (back-compat). A PM subscribed to both a coord repo and impl repos sets this to its impl repos so a coord-repo push/CI event doesn't self-wake. |
| `drop_title_all_of` | list<list<string>> | `[]` | **`coord-message` family.** Drop (no intent, no wake — before the recipient gate) a coordination subject whose **title** contains **every** substring of any one group (AND within a group, OR across groups) — for bookkeeping-title noise (e.g. `[["Rule E back-merge sync","paper-trail anchor"]]`). Substrings lowercased for case-insensitive matching; a non-list group or an empty substring **throws** (an empty group is ignored). **Blast radius:** for an `issue_comment` the title is the *parent issue's* title, so a matched group also suppresses every comment on that issue — intended for a pure paper-trail anchor (all its activity is noise), but keep groups specific enough not to swallow a live-discussion thread. Empty/absent ⇒ no subject dropped. |
| `wake_membership` | list<string> | `[to_me, to_all, comment_to, bare_reply_to_own_thread]` | **`coord-message` family (DL-190).** Which classes grant coord-message **live-wake** (channel_push): `to_me` (a `to:<me>` label), `to_all` (`to:all`), `from_me` (`from:<me>` — ALL activity on a thread you opened; the wide over-wake knob, still **opt-in**), `comment_to` (DL-192 — a body-`TO:<self>` grant, see below), and **`bare_reply_to_own_thread`** (DL-235, default-ON) — a **BARE** reply (no `TO:` line at all) on a thread you opened grants membership, **and only when the body's `FROM:` line is someone else**. That third clause is an **echo guard**: under a shared account every seat posts as one identity, so actor id cannot distinguish your own comment from a counterparty's, and an authorship-keyed grant without it self-wakes on your own follow-up — which is precisely why DL-213 ruled `from_me` the wrong knob and kept it opt-in. `bare_reply_to_own_thread` is the narrow form: bare-only, own-thread-only, echo-guarded, so it grants exactly `reply-dir B` and nothing wider. The unconditional narrow still outranks it — an explicit `TO: someone-else` denies membership even on your own thread. **DEFAULT `[to_me, to_all, comment_to, bare_reply_to_own_thread]`** — `comment_to` is **default-ON since DL-213**, `bare_reply_to_own_thread` since DL-235 (the post-a-reply-and-wait flow — post to a counterparty, wait for their directed reply — is otherwise dark out of the box). **`from_me` stays OUT of the default** — it is the over-wake/self-wake knob: a coordinator opening many threads would else wake on every reply to them. Add `from_me` to also live-wake on **all** activity on threads you opened (a `from:<me>` issue label) — this is **operationally required, not optional, for a PM/coordinator seat** that opens briefs labeled `to:<impl>` (never `to:<self>`) and must live-wake on the impl replies to them; without it those brief-reply wakes downgrade to SessionStart-only pickup. Note: a comment's direction lives in its **body `TO:` line**, not as a `to:<me>` issue label. The body-`TO:` check is three-state (`RecipientAddressing::addresses`): a comment addressed to **someone else** always *narrows* (denies membership, unconditional); a comment with **no** `TO:` line falls back to label membership; and a comment addressed **TO you** grants membership **when `comment_to` is set** (default ON since DL-213). So only if you set `wake_membership` explicitly and OMIT `comment_to` does a directed reply on your own thread shift from live-wake to SessionStart (`from:<self>` / `protocol:invalid`) boundary pickup — `bridge:check` warns on exactly that explicit-narrow config. **`comment_to` (DL-192)** is precisely that grant: it live-wakes on a comment whose body says `TO: <self>` **even when the thread labels don't address you** — closing the cross-thread pull-in gap (a loop-in on a thread you neither opened nor were labelled on) that no label-class can express, since the `to:` label freezes at thread-open. It grants only (and keys on the directed `TO:` line, not authorship, so it is echo-safe under a shared account); the narrow (`TO:` someone-else) and the no-`TO:` label-fallback are unchanged, so `comment_to` is purely additive. This gates membership only; inbox-staging is unchanged. Values lowercased. **UPGRADING:** an install with **no explicit** `wake_membership` will start live-waking on comment-directed replies after DL-213; set `wake_membership` explicitly (omitting `comment_to`) to keep them dark. |

## 3. Secrets, tokens & state files

### Handling a secret VALUE (not just its file)

Every path in the table below holds a value that must never be **resolved onto a readable surface**: stdout (a terminal scrollback, a CI log, an AI agent's session transcript), an **argv** (`/proc/<pid>/cmdline` is world-readable, so a value passed as a command-line argument to any non-builtin is readable by every local account for the life of the process), a log line, or the **shell history** file a command-line literal lands in. The instrument does not matter and the list of instruments is never complete — the next thing that resolves a secret has not been enumerated yet — so the rule is stated over the surface instead:

- **Placing a value.** Type it into `read -rs`, then write it with a shell **builtin**: `read -rsp 'value: ' V; printf '%s' "$V" > <path>; unset V`. `read -rs` keeps it off the terminal and out of history; `printf` forks nothing, so there is no argv to read. Create the file under `umask 077` (or `chmod 600` it immediately) — the receiver 500s on a group/world-readable HMAC secret (`secret_perms_insecure`, DL-010) and every token path in the table is read fail-closed.
- **Passing a value to a program.** Give it the **path**, or feed it on **stdin** — never as an argument. `curl` takes an `Authorization` header on stdin: `printf 'header = "Authorization: Bearer %s"\n' "$TOKEN" | curl --config - …`.
- **Testing for one.** `${VAR:+set}` or `[ -n "$VAR" ]`. `${VAR:-…}` and `echo "$VAR"` print the value they were meant to test.
- **Comparing two copies.** Compare digests — `sha256sum < <path>` at each end — never the values.
- **Reading one back.** Open the file yourself, at your own terminal. Do not `cat` it in a session an agent or a logger is recording: once a value reaches a transcript it is leaked whether or not anyone reads the file again, and the only repair is rotation.

⚠ **CI carries a BACKSTOP under this section, and a green run of it is not compliance with this section.** `bin/check-doc-secret-fences.py` (workflow `doc-fence secret backstop`, DL-324) parses the **shell code fences** of every `*.md` and fails a PR that resolves a secret VALUE onto one of the four surfaces above. It reads fenced shell only — never inline backticks, never prose, never a `.php`/`.sh`/workflow `run:` block. **One leg of it is not an enumeration:** where a pipeline carrying a secret VALUE *ends* is decided **deny-by-default** — the tail leaks unless it is a known stdin **sink** (a digest, a file write, a network send, a program that resolves the value itself), because the list that named the *leaking* tails instead had SILENT gaps and one added pipe stage turned a caught leak into a clean run (`base64 <secret file>` red, `cat <secret file> | base64` green — likewise for a list of other filters that the tool's own BOUNDS docstring owns; it is not restated here, because the three copies of it had already diverged). That leg is therefore wrong in the loud direction: an unlisted tail **reds** and the doc waives the line with a reason, and what may JOIN the sink list is itself a stated test — an instrument this section prescribes, or one this repo's runbooks use, never one added on plausibility. Every other leg is still only the spellings someone has already seen. It caught 5/5 of the fence-resident members of the class that have actually occurred and produced zero false positives over this repo's whole tag history — a measurement re-run over 85 tags / 1,973 tag-file pairs after the deny-by-default inversion, which reddened nothing the enumerating version did not (reproduce it with `python3 bin/doc-fence-census.py`; run 2026-09-01) — which is why it exists; every other leg is still a grep over an enumeration, which is why **this section is the rule and the check is a net underneath it**. The check tells you which surface you reached; it cannot tell you the class is absent, and the next instrument that resolves a secret will not be on its list. If a doc must SHOW a bad form, put it in inline backticks in prose (which the tool never reads) — that is what every explanation of these defects in this repo already does.

Absent/false ⇒ `reopened` stays the `opened` outcome (byte-identical). That reverse line never degrades to a disclosure: its family term is a positive map read, so an unread agent can only silence it. Absent ⇒ byte-identical. See `docs/writeback.md`. **`coord_card_lane_stage_ids`** (card#6371, optional object `{"now"\|"next"\|"later"\|"maybe": <stage_id>}`) makes the create stage **lane-derived** on a board with a priority-lane model: a coord card for an issue whose title starts with `[TASK]` is created in the stage its **`stage:*` label** declares instead of at `coord_card_stage_id` — without it the bridge pins every card to that one stage, and the consumer's board→issue writeback (which runs BEFORE its issues-sync) rewrites the issue's `stage:*` label to match that stage (measured: 9 issues flipped to `stage:now`). The create path fires on `issues.opened`/`reopened` only, so a `[TASK]` labelled after filing is carded in `later` — and, without the opt-in `coord-card-relane` family, its label is then converged to match. **Since card#6393 these ids are read by three writes, not one:** create, the `move_coord_cards` **revive** (a reopened `[TASK]` returns to its declared lane, not to the fixed `coord_card_stage_id`), and the `coord-card-relane` **lane→lane** move — which additionally REQUIRES them: with no lane model that family classifies nothing at all, and `bridge:check` warns for an install that enables it without them — and, since card#8290, reports the reverse direction (a lane model no agent runs that family on) as a green advisory naming the post-birth race it leaves open, never as a warning. A **revive is fail-closed on provenance**: only a **service-set** terminal (`last_stage_move.actor_type === "service"`, an allow-list) is reversed, and only from that terminal — a human's closure intent, an unknown/absent actor, or a card someone has moved on is never touched.

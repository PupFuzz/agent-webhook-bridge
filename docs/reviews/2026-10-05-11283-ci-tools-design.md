# Design note — card#11283: CI tools served without `board_tools`, default-on, in the client pack

**Status:** DRAFT, before design review. No code yet. **Card:** bridge board 8 #11283. **Base:** `dev` @ bfd41204.
**Related:** DL-217/222/225, DL-229, DL-430/434/445 (pack + update door), DL-451, DL-452, card#11282.

## 0. What the code says today (it changes the card's premise)

- **Every door keys identity on an ENABLED `board_tools` block.**
  - HTTP: `BoardToolAgentResolver::__construct` indexes only enabled `http` blocks.
  - ssh: `ToolsCallCommand::handle` refuses a non-"live ssh board-tools agent", and does so before its `op` branch.
  - The update door shares both credentials (`AgentToolsController::authenticate` serves `call` and `client`).
- **⇒ An agent with no enabled `board_tools` cannot reach the update door, so it is not on the self-updating client.**
  Measured: prod 0.96.0 `bridge:client-fleet` says "no agent has an enabled board_tools block". Outcome 3 needs a door
  identity that is not the board scope. There is no update credential to reuse, because none exists apart from it.
- **The CI tools touch no board.** `CiAwaitTool::call` / `CiAwaitCancelTool::call` receive `$cfg` and `$client` and use
  neither. The agent is `CallingSeat`, sealed in `BoardToolDispatcher::dispatch`. Delivery goes through
  `AuthoredIntentPush::send`, which reads `channel` config only.
- **The dispatcher couples them anyway.** It calls `WritebackClientFactory::make()` before every tool, so an install
  with no writeback token 503s `ci_await`. It also stamps `ConfigSeenLedger::recordEnabled`, which records "a
  `board_tools` block exists".
- **Advertisement is env-only.** `shouldAdvertiseTools()` in `agent-webhook-bridge-channel.mjs` advertises all of
  `TOOL_DEFINITIONS` once any transport is set. `client-capabilities.json` is a version table used for refusal text
  (`ClientCapabilities`), not per agent.
- **The pack already carries `bridge-board-call` and the CI definitions** (`examples/channel-servers/bin/`,
  `TOOL_DEFINITIONS`). Reaching the door is the gap, not the pack's contents.

## 1. Config shape — recommend: split the DOOR from the BOARD SCOPE; `ci_tools.enabled: false` opts out

- **`ToolsDoorConfig`** takes the door half of `BoardToolsConfig` (`transport`, `tokenPath`/`bearerFromChannel`,
  `sshAccount`, `fleetView`, `clientUpdateApprovalRequired`). It is parsed from a new per-agent `tools_door:` block.
  All three doors resolve through it. `BoardToolsConfig` keeps board, swimlane, stages and tags only.
- **When the door is on:**
  - `board_tools` enabled ⇒ the door is what its keys say today (no YAML edit on board-tools installs).
  - Otherwise `tools_door` absent ⇒ default-on: ssh serves `--agent=<name>` (the pinned key is the gate); HTTP
    indexes `channel.auth.token_path` when set (DL-222's `bearerFromChannel` rule).
  - `tools_door: {enabled: false}` turns the door off, update door included.
- **`ci_tools: {enabled: false}`** removes `ci_await`/`ci_await_cancel` on every door. Absent ⇒ on, including beside
  an enabled `board_tools`.
- **`ServedTools::for(AgentConfig)` is the one served-set primitive.** The dispatcher refuses any other name
  (`not_served`) before tool resolution, before a writeback client is built, and before the `ConfigSeenLedger` stamp.
- **Split the interface.** CI tools implement `SeatTool::call(args, agent)`, which receives no `BoardToolsConfig` and
  no `KanbanClient`.
- **Cost, named.** Door keys have two spellings for a deprecation window (`board_tools.*` and `tools_door.*`). ONE
  parser reads both, a contradiction is a load error, and `bridge:check` warns on the old spelling. Rejected: a
  scope-less `board_tools` tri-state, because it keeps the credential owned by the board scope.

## 2. Authentication — recommend: reuse what seats hold; add an ssh pin only for UDS-only seats

- **ssh key: reuse it.** `--agent` is host-pinned; widening "live ssh board-tools agent" to "door enabled" adds no
  credential.
- **Channel token: reuse it on HTTP**, as DL-222 does. It is a per-agent secret shared by bridge and seat, so it grants
  only the seat's own identity. Collisions stay one index across both blocks (`BoardToolAgentResolver`, second pass).
- **Update-door credential:** has none of its own (§0).
- **Smallest addition:** for a seat with neither (UDS, no token; e.g. §6), an ssh forced-command key via
  `provision-board-tools.py`, extended to CI-only agents. The fallback is a `tools_door.auth.token_path` bearer if the
  loopback HTTP door is reachable. The operator pin is still needed: it IS the credential.
- **Boundary.**
  - A CI-only agent gets its own awaits, its own `ci_settled`/`ci_await_expired`, and the update door (`client_fleet`
    stays behind `fleet_view`).
  - It gets no board read or write, by construction (§1).
  - ⚠ **Residual:** `ci_await` accepts any repo the INSTALL receives (`CiAwaitService::receivedRepo`), and
    `ci_settled` carries that repo's workflow names, conclusions and URLs. DL-452 shipped this to board-tools agents;
    this card extends it to impl seats. → **Q2**.
  - On a same-user box the door is not the only boundary: the account can already read the bridge's secrets.

## 3. Advertisement — recommend: ask the bridge once at start; never a static list

- **Why not static:** the served set is bridge-side config the seat cannot read (DL-229), so a static list
  advertises tools that refuse.
- **Add `op: served_tools`** to the update door, answered by `ServedTools::for`. It never goes through the dispatcher,
  so board state cannot block it.
- **The channel server calls it once before `mcp.connect`**, under a bounded deadline (`MANIFEST_LEG_MS` shape), and
  advertises `TOOL_DEFINITIONS ∩ served_tools`.
  - Timeout or malformed answer ⇒ no bridge tool advertised, with a stderr reason (`clear_context` unaffected).
  - An older bridge's well-formed unknown-op 4xx ⇒ today's env rule, which is correct there because only board-tools
    agents can authenticate to it.
- **Residual:** a mid-session config edit refuses a tool advertised at start; the refusal says "restart". Whether
  Claude Code honours `tools/list_changed` was not verified.

## 4. Distribution

- **A seat on a client root whose door now resolves** gets the new server, CI definitions and `bridge-board-call`
  shims at its next launch (`runLaunchUpdate`), with no step.
- **An impl seat with no board tools is on no client root today (§0).** It needs ONE
  `provision-board-tools.py --role b --bootstrap-client` (or `--certify-only`), after which updates are automatic.
- **Certify with `served_tools`** instead of `--self-cert`'s `board_my_cards`, which a CI-only agent is not served.
- **An older client** on a CI-only agent advertises board tools, and they refuse `not_served`. That is safe but breaks
  outcome 4 until it updates, and DL-445's client-half line warns.
- **A standalone/OUTBOUND copy** never updates until bootstrapped.

## 5. `bridge:check`

- **New per-agent leg `ci_tools.agent`:**
  - **served**, naming the door (with `SshPinnedLineCheck`);
  - **opted out** — silence plus the reason;
  - **default-on but unreachable** (no token, no pin seen) — warn with the provisioning command;
  - **bearer fault** — `BoardToolAgentResolver::bearerSeverity`.
- **`workflow_run`:**
  - `GitHubWebhookSubscriptionCheck` reads the matched hook's `events` from the list it already fetches (no new call)
    and warns when `workflow_run` is missing while any agent is CI-served.
  - `CiAwaitsCheck`'s stored-delivery warn stays as the fallback evidence.
  - That the hook list carries `events` is from recall; verify it at build.
- **Re-key** `ClientFleet` and `ClientFleetCheck` from "enabled `board_tools`" to "door enabled".

## 6. Upgrade and migration

- **Board-tools installs:** no change.
- **Agents with `board_tools` absent/disabled that hold a channel token gain an authenticated HTTP door on upgrade.**
  That changes what the system accepts. UPGRADING names it and the opt-outs. → **Q1**.
- **This host — seat `kanban`, agent `prod-agent`:**
  - Config: `board_tools: enabled: false`, a UDS channel with no token, and no `github` subscription
    (`kanban-solo-ci`/`writeback-agent` receive the repos, which `receivedRepo` accepts install-wide).
  - `~/.mcp.json` runs the server repo-direct from the prod checkout, so the code arrives with the deploy plus a
    restart. A stray `~/.local/share/agent-webhook-bridge/client/kanbanboard-agent/install-log.jsonl` with no
    `versions/` is unexplained.
  - **Steps:** deploy → `--role a` as `kanban` itself pins a forced-command key for `--agent=prod-agent` (allowed: "a
    non-root account may only pin into ITS OWN authorized_keys"; sshd listens on :22; no `authorized_keys` exists
    yet) → set `BRIDGE_TOOLS_SSH_TARGET`/`_KEY` in the seat's `.mcp.json` env → restart → `bridge:check` shows
    served, and `tools/list` shows `ci_*` and no `board_*`.
  - The samebox wrapper is cross-user and root-run, so it does not fit here.

## 7. Test plan (each seen to fail first; the deliberate break is in brackets)

- **T1.** A CI-only agent calls every board tool name on both doors → `not_served`, with `Http::preventStrayRequests()`,
  no `WritebackClientFactory` call and no `BoardToolsConfig` built. [add board tools to the served set]
- **T2.** `ci_await` succeeds with no writeback token. [today's code: a natural 503 red]
- **T3.** No argument names another seat, and cancel touches only own rows. [accept a `seat` key]
- **T4.** `ci_tools.enabled: false` → refused on both doors and absent from `served_tools`. [ignore the flag]
- **T5.** Property over board × ci × transport × door: `served_tools` equals the set the dispatcher serves.
  [hard-code one side]
- **T6.** A cross-block bearer collision → both refused; an unknown bearer → 401.
- **T7.** ssh with `tools_door.enabled: false` → exit 2; a CI-only agent → served. [keep the old check]
- **T8.** A CI-only call stamps no `ConfigSeenLedger` row. [stamp it; `BoardToolsLostCheck` false-alarms]
- **T9 (node).** Advertise exactly `served_tools`; a timeout gives none; an old-bridge 4xx gives the env rule.
  [static list]
- **T10.** The update door serves a CI-only agent; `client_fleet` → 403 without `fleet_view`; approval honoured.
- **T11.** No new GitHub request from `served_tools`, the doors or the check legs. [assert the request count]
